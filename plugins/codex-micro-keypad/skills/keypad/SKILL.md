description: Show a standalone Codex Micro keypad or control Codex chats through native software interfaces without a virtual HID driver. Use for 小键盘, model/reasoning controls, sending a requested message, stopping a turn, and replying to a specific approval.

Call `get_keypad_capabilities` before presenting supported operations. Call `show_keypad` to display the native Micro keypad with its existing keycaps, rotary control, joystick, and tray/menu bar. The Windows distribution uses WPF; the separate macOS preview uses UIKit / Mac Catalyst with an AppKit bridge. Both have control and monitor panels. Do not replace the keypad with a new dashboard or form. Use `list_keypad_threads` to resolve the intended chat and `get_keypad_state` to inspect its model, turn, and pending approvals. Existing-chat controls require an exact thread ID; do not substitute the most recent chat for an ambiguous target.

The software adapter supports chat selection, new drafts, guarded forks, Fast, single command/file approvals, the reasoning dial, and quick-model pairs on existing chats. Message submission with explicit text and exact-turn interruption are separate from native composer submission. Platform capabilities differ; never infer support from the presence of a physical key. Compilation does not establish live UI behavior or complete Micro feature parity.

On macOS, `get_keypad_ui_state` observes the exact native window/composer and returns a short-lived `targetToken`. Read `get_keypad_models` first to resolve draft settings. Pass that token as `target_token` for native composer submit, navigation, Skill insertion, Sketch, dictation, and blank-draft settings. These operations require Accessibility permission, an unambiguous native target, and readback. Never fall back to title matching, coordinates, another chat, or a newly fabricated token. Draft effort/Fast/Plan use observed native Power, Speed and Plan controls with readback; configured shortcuts are optional. A confirmed ID-less composer supports these settings without inventing a thread ID, but cannot authorize chat-specific actions. `insert_keypad_skill` verifies visible insertion, selects the inserted atom, copies it back, and checks the exact HTML mention name and path. If structural verification is unavailable, treat the outcome as unknown and do not retry. Native UI business acceptance remains pending because computer-use access to the Codex app was blocked during development.

On macOS, live local and hotkey-window client routes can expose `clientThreadId` separately from `threadId`. A `client-new-thread:<UUID>` identifies the current native composer; it is not proof of an unsent draft or a server thread UUID. When `nativeComposer=true`, use only native model/Fast/Plan/reasoning controls with the current token and `native_composer=true`. A different client route invalidates that token even when the window and composer elements are reused. Do not convert client IDs into UUIDs, submit, stop, approve, fork or assign a task slot from temporal proximity. Foreign, empty or repeated `hostId` parameters cannot authorize local thread controls or stale IPC fallback. Exact `hostId=local` and an omitted host share local identity.

On macOS, `get_keypad_client_thread` can resolve an observed local client route to its exact stored UUID. Supply `client_thread_id` and the `roster_scope` returned by `list_keypad_threads`. The lookup checks persisted forward/reverse bindings, an exact local server record, and account/storage/binding stability. A missing result does not prove an unsent draft. The panel may display/copy the verified UUID and offer it for explicit task assignment, but native controls still require the current composer token; the binding does not authorize submit, stop, approval or fork. Do not use global home-draft records to infer which window owns a draft.

On macOS, mixed client/server document and sidebar routes are only binding candidates. Read `list_keypad_threads` before `get_keypad_ui_state` so the backend can verify the exact alias in the current account. An unresolved `bindingObservationToken` is never a control token. A confirmed alias stays settings-only; every write rechecks scope, binding, window, composer and native token.

On macOS, a new-chat launch acknowledgment is not a confirmed draft. Retire the previous thread ID immediately. Use the returned `foreground` only when `navigation_verified=true` and it confirms a draft; otherwise wait for new native evidence. Old IPC visibility, delayed activity replies and a failed native read cannot restore the previous ID. After native identity has been observed, losing it leaves the current identity unknown; only an account/lifecycle reset permits initial IPC discovery again.

On macOS, hotkey home and hotkey new-chat routes require their own visible composer rather than the main home container. Project drafts require the observed home composer and a single local projectId; changing that project invalidates the native target token. Loading pages without a composer, foreign hosts, ambiguous project scopes and legacy panel redirects do not authorize draft controls. Always use the returned draft flag and token instead of inferring a draft from a URL alone.

On macOS, pin/unpin, native Markdown copy, archive, terminal, browser-tab and side-chat operations require both the exact foreground `thread_id` and its current UI token. Read the relevant `canOpenThreadMenu`, `canToggleTerminal` or `canOpenBrowser` flag. Archive leaves Codex confirmations untouched and reports success only after exact archived-list readback. Markdown copy reports confirmation and character count, never the copied text. Native panel commands do not type terminal commands or open arbitrary URLs. Settings, Skills and scheduled-task management use fixed Codex page links; launch acceptance and exact page verification are separate. Opening task management does not create or run a task. Side chat requires a new visible panel with a ready composer in the same parent chat; its panel ID is not a child thread ID, and opening it does not send a message.

On macOS, `open_keypad_feedback` requires `canOpenFeedback` and a current UI token; it verifies the specific feedback form without entering details, changing consent, or submitting. `open_keypad_files` requires `canOpenFiles` and the token of an exact chat or confirmed draft. It opens the native Files and folders picker and reports `awaitingSelection=true`, `attachmentVerified=false`; file selection and attachment completion are not verified by this handoff. A native modal blocks stale visible-chat fallback. Do not substitute the general files picker for the separate photos command. `open_keypad_photos` requires `canOpenPhotos` and the current token. It uses an observed Add photos item or an explicitly configured native `composer.addPhotos` shortcut, rechecked before input; no default shortcut is guessed or configured automatically. It must observe a new unique Select photos dialog, reports `pickerKind=photos`, `imagesOnlyRequested=true`, and still reports `attachmentVerified=false`. Missing or wrong pickers, extra permission modals and unknown shortcut outcomes never trigger a retry or general-files fallback.

On macOS, `open_keypad_commit`, `open_keypad_branch`, `open_keypad_pull_request` and `open_keypad_draft_pull_request` require the exact foreground thread ID, current token and `canOpenGitWorkflow`. They select the distinct native command only inside one observed Project group, excluding same-named chat results, and return `workflowStage=branchSetup|commitForm|pullRequestForm`. Commit/push and both PR commands may first require the Work here branch form; at that stage `prDefaultVerified=false`. Only an actual PR form with its correct selected regular/draft action yields `prDefaultVerified=true`. The commit/push form has three distinct actions and may omit the commit-message field in push-only mode. `workflowOpened=true` with `mutationCompleted=false` confirms a native form only. They do not type, change form options or file scope, create a branch, commit, push or submit. Do not select a form's final action merely to imitate opening the workflow.

On macOS, `run_keypad_environment_action` requires `canRunEnvironmentAction`, the exact foreground thread ID and current token. It selects the first platform-applicable configured action from the unfiltered Project command group, not the toolbar's recently used Run action. Nonempty or unreadable search, missing or ambiguous groups, and changed actions are unavailable. It rechecks the exact `environmentAction1` terminal in the same chat. `runRequested=true`, `terminalVerified=true`, `executionVerified=false` confirm native execution handoff only; no shell exit status is claimed. Do not retry an unknown outcome or substitute another action.

`open_keypad_merge_pull_request` uses the exact foreground thread ID, token and `canOpenGitWorkflow`. It selects Merge PR only from the unique Project command group, then verifies the specific confirmation and displayed squash / merge-commit choice. It does not change the method or press the final merge button. `workflowStage=mergeConfirmation`, `mergeCompleted=false`, `pullRequestIdentityVerified=false`: the native confirmation does not expose a verified PR number, and its surrounding random panel ID is not a PR ID.

On macOS, `insert_keypad_preset_text` accepts only `preset=YOLO|YEET` and the current native token when `canInsertPresetText=true`. It writes the fixed `:yolo:` / `:yeet:` literal at the observed UTF-16 caret or selection in an exact chat or confirmed draft. It never submits, changes permissions, or uses the clipboard. Missing or invalid selection, changed text/target/focus, or unverified text/caret readback must fail; unknown input outcomes must never be replayed. An ID-less fallback composer remains settings-only. The preset names do not authorize permission bypass.

On macOS, task mappings are local Micro preferences with 14 stable positions, scoped by the observed account, execution host and storage root. `list_keypad_threads` returns `rosterScope`; passing `mapped_thread_ids` (at most 14 exact UUIDs) with that same `roster_scope` resolves older stored chats separately from recent chats. A scope mismatch never queries the saved IDs. Missing entries remain empty slots and retain their saved IDs; never substitute a recent chat or a same-named chat. Resolving mappings is read-only and does not navigate, resume a turn, pin, archive, or change Codex configuration. The custom mapping editor can copy the current recent list explicitly, choose a specific full ID or clear an individual slot.

On macOS, each custom task slot can instead hold a supported command, including recentThread1 through recentThread6. A recent command follows that exact position in the local recent catalog; missing positions stay unavailable. Hover and press retain the displayed exact target until the interaction ends. Other commands use the same current-target guards and native/IPC controls as action keys. Command assignments and fixed IDs are mutually exclusive and account-scoped; replacing or clearing a slot retires its captured action. Assigning a fixed chat moves it out of its previous slot in the same scope. Commands are never passed as mapped_thread_ids. New-chat commands remain commands; no pending draft-to-thread assignment is inferred without an observed matching client thread identity.

On macOS, `list_keypad_threads` with `include_pinned=true` additionally returns up to 14 `pinnedThreads` and `pinnedAvailable`. It combines the exact local modern pinned section with pinned local project members from read-only `project/list` and `thread/list(projectId)`. Saved sidebar preferences determine placement, never identity or membership. Local project migration aliases use the current server's exact storage-root namespace. Manual placement preserves project positions and native individual-pin order; recency sorting happens before truncation. Individually pinned chats are excluded from project members. Manual project order uses the saved list or the previous validated order in the same account and connection. A supported complete section list with no individual pin section can still supply pinned projects. Missing identity, malformed/incomplete catalogs, unsupported required protocols or changed placement during enumeration cannot produce partial executable slots. Missing projects and native ChatGPT project mirrors are omitted; cross-host/cloud projects and legacy pin migration remain outside this local source. No project, pin, preference or membership writes occur.

On macOS, `include_priority=true` on `list_keypad_threads` reads the complete local interactive catalog across pages and returns `priorityComplete=true` only after the last page. Malformed, duplicate, looping or incomplete bounded catalogs fail, rather than ranking a successful-looking prefix. Each row includes attention and native recency: waiting (approval/question), unread, active, idle; same-rank ties use recency descending and retain source order when equal. Visual lamp status is independent, so an unread running chat still shows running. The activity stream publishes an `attention` map and advances its revision even if only unread attention changes. Owner discovery rotates all candidates in batches of eight with interleaved reads, at most 64 requests outstanding and a per-thread cooldown; rollout observation runs incrementally off the control queue. No navigation, task resumption or acknowledgement occurs during ranking.

On macOS, visual lamp precedence is error, approval, question, running, unread, idle. `get_keypad_ui_state.appFocused` reports current physical application focus; `foreground` may retain submission focus when Micro itself is clicked and must not be used to hide unread. The panel hides only the selected unread lamp when fresh native focus, exact thread ID and route agree. It does not clear unread evidence, change attention ranking or send acknowledgements. Unknown, expired or contradictory focus retains the unread lamp; disconnected or removed rows cannot reuse a cached colored lamp.

`get_keypad_activity` reads the macOS compact live status stream after `list_keypad_threads` configures observation. IPC patches and bounded rollout/global-state file events update activity independently from model/catalog calls. Unread state requires the exact current account and local host bucket; unknown values are not idle, complete, or unread.

Windows reads the live document route and native accessibility selection metadata; title fallback requires a unique local thread. macOS reads exact live route UUIDs and rejects bootstrap URLs, conflicting routes and stale visible-thread fallbacks. Native draft and ID-less composer settings have separate identity guards. Each adapter rechecks the target before mutation. Question answers are reconciled against accepted IPC state; queued/failed answers do not clear the waiting signal.

Use `get_keypad_models` before choosing a model or reasoning effort. Changes affect the next turn; preserve other thread settings and permissions. Existing-chat operations reuse the current desktop owner. Native macOS operations use an isolated Accessibility adapter and PID-targeted native shortcuts; they do not emulate HID hardware or inject renderer scripts.

Opening the window or installing the plugin does not authorize sending messages, forking chats, stopping a turn, or approving commands. Perform those actions only when requested. Before an approval, read the current request and pass its exact request ID and the user's decision. Never automatically approve an unknown request, a batch, or a future request. Before stopping, pass the exact active turn ID.

Do not automatically retry mutations after a timeout or disconnection; report the unknown outcome and read the current state. A protocol mismatch requires an update, not input simulation. The standalone window and MCP tools share the same control implementation, but each has an explicit target.
